# 在线双人对战需求文档（草案）

> 状态：待确认；本文定义产品需求与验收边界，不表示功能已经实现。

## 1. 目标与现状

新增两名已登录用户通过不同浏览器或设备参与同一局五子棋的模式。双方看到同一棋盘，轮流落子，服务端裁决胜负；刷新页面或后端重启后仍能恢复对局。

现有大厅中的 `TWO` 是“玩家对 AI”的经典模式，不能作为在线双人的现成实现。现有 `/api/game/*`、`GameService` 和 `active_game` 以 `user_id` 管理一名用户的棋局；在线对战需要独立的、以 `match_id` 为中心的共享对局模型，同时保留五种现有模式的行为。

第一版优先做到“能稳定完成一局”，不以增加 Redis 等组件为目标。

## 2. 第一版范围（MVP）

### 包含

- 大厅新增“在线双人”入口，与现有经典对弈、三人及特殊棋盘模式区分。
- 已登录用户创建房间，获得可复制的房间码；另一名已登录用户输入房间码加入。
- 房主执黑、加入者执白；两人到齐后开始，使用现有经典模式的 15×15 棋盘及适用的落子、禁手和胜负规则，不调用 AI。
- 双方显示玩家昵称、执子颜色、当前回合、落子、结果及连接异常提示。
- 服务端验证每一步并持久化；客户端仅提交落子意图，不自行决定合法性或结果。
- 双方通过查询接口同步对局；浏览器刷新或后端单实例重启后可恢复到同一局。
- 支持房主在开局前取消房间、开局后主动认输；断线不自动判负。
- 记录在线对局的最终结果，防止重复结束或重复记账。

### 不包含

- 自动匹配、排位、观战、聊天、好友系统、多人特殊模式、多人同时操控同一账号。
- 双人悔棋、暂停、自动判定掉线负、棋局计时器；这些涉及双方同意与超时规则，留待后续版本。
- Redis、消息队列、多后端实例、跨实例消息分发。第一版仅运行一个后端实例。
- 默认不把在线对战结果计入现有 AI 积分；若决定计分，需先确定积分规则并完成双人幂等结算设计。

## 3. 用户流程与状态

1. 玩家 A 从大厅创建房间，进入等待页，复制房间码。
2. 玩家 B 登录后输入房间码；服务端确认房间未满、未过期，且 B 不是 A。
3. 加入成功后房间状态由 `WAITING` 变为 `PLAYING`，A 执黑先手，双方进入对局页。
4. 当前回合玩家落子。服务端校验并保存后，两端同步最新棋盘与版本号。
5. 五子连线、平局或一方认输后，状态变为 `FINISHED`，双方看到相同结果；重复请求不能再次结算。
6. 任一方刷新或短暂断网后，重新登录/进入对局页并读取服务端状态，回到正确棋局；另一方不能趁机越权代下。

房间码仅用于寻找房间，**不是授权凭证**。任何读取或操作对局的请求都要校验登录用户是否属于该局。

## 4. 功能要求

| 编号 | 要求 | 验收重点 |
| --- | --- | --- |
| PVP-01 | 创建房间时生成不可轻易猜测、短期有效的房间码 | 房间码不重复；过期或取消后不能加入 |
| PVP-02 | 房间最多两名不同账号玩家 | 同账号加入自己房间、第三人加入、重复加入均被正确处理 |
| PVP-03 | 服务端确定座位与先后手 | 双方看到相同的黑白分配和当前回合 |
| PVP-04 | 服务端校验身份、回合、坐标、空位、禁手及棋局状态 | 非参与者、非当前玩家或非法落子不改变棋盘 |
| PVP-05 | 每次成功落子使对局版本号递增 | 过期版本请求被拒绝，客户端重新拉取状态 |
| PVP-06 | 棋盘、玩家、状态和结果持久化 | 浏览器刷新及单后端容器重启后可恢复 |
| PVP-07 | 一方认输或棋局自然结束时只生成一次最终结果 | 并发结束、重复点击、网络重试不会重复记录 |
| PVP-08 | 客户端提示等待对手、轮到自己、网络断开、对手认输等状态 | 不把“暂时断线”直接展示为“已判负” |
| PVP-09 | 现有 AI 模式接口和数据不受影响 | 原有游戏回归测试继续通过 |

## 5. 数据与接口约束

- 使用新的 Flyway 迁移增加在线房间/对局表，不直接把共享棋局塞进现有以 `user_id` 为主键的 `active_game` 表。
- 对局至少包含 `match_id`、房间码、黑白双方用户 ID、状态、当前回合、棋盘快照、`revision`、创建/更新时间和结束结果。必要时另存落子流水，便于排查与回放。
- 在线对局结果与现有 AI `game_result` 分开设计：该表当前以 `game_id` 为主键，只能表示一名用户的一条结果，不能直接写入双方两条记录。
- 建议独立 `/api/online-matches/*` 接口，至少提供创建、加入、查询当前局、获取对局状态、落子、取消/认输。具体路径和响应字段在接口设计阶段确定。
- 落子请求提交 `matchId`、`row`、`col`、`expectedRevision`；发生版本冲突时返回明确错误和可重新获取的最新状态，不接受客户端提交“落子后棋盘”或“胜负结果”。
- 每一步应在数据库事务内完成“锁定/比对版本 → 校验 → 更新棋盘与回合 → 判断结果 → 提交”；成功提交后再供两端读取。仅靠进程内 `ReentrantLock` 不足以保证后端重启后的状态一致。
- 第一版仅支持同一账号同时参与一局未结束的在线对局；与已有 AI 对局是否允许并行，由实现时明确并在大厅给出提示。

## 6. 同步、权限与部署

- **MVP 同步**：对局页可见时约每 1–2 秒查询一次状态；落子后立即刷新。页面隐藏、离开对局或棋局结束时降低频率或停止轮询。请求失败时提示并退避重试，不连续高频重试。
- **权限**：沿用当前 Spring Security 登录 Session 与 CSRF 防护；创建、加入、落子、认输均须服务端鉴权。不能通过猜测 `matchId` 读取他人棋局。对房间码加入操作设置合理限流。
- **网络恢复**：客户端重连后以服务端快照及 `revision` 为准；旧请求或重复提交不得形成第二次落子。双方在线状态若仅由轮询推断，应标为“连接可能中断”，避免误判。
- **部署边界**：当前 Compose 仅绑定宿主机 `127.0.0.1`。本机两个独立浏览器会话可验收功能；要让不同设备或外网用户访问，还需部署到双方可达的地址，并配置 HTTPS、访问控制及对应的反向代理。
- **后续实时推送**：规则和数据模型稳定后，可用 Spring WebSocket/STOMP 推送落子与状态；查询接口仍保留给首次加载和断线恢复。WebSocket 上线时须检查握手、消息订阅权限及 Nginx Upgrade 代理配置。Redis/外部消息代理仅在多实例扩容确有需求时评估。

## 7. 验收场景

1. 使用两个不同账号、两个独立浏览器会话：A 创建、B 加入，双方均看到同一棋盘且黑先白后。
2. 测试非参与者访问、同账号自加入、满房加入、未轮到自己、越界/重复位置、过期房间码，均不得改变对局。
3. 双方几乎同时提交落子，最多只有符合当前回合与版本的一步生效，双方最终棋盘一致。
4. 某次落子请求超时后重试，不能在同一回合多落一子；客户端能获取最新状态继续玩。
5. 浏览器刷新及 `docker compose restart backend` 后，两名玩家都能恢复同一未结束棋局并继续落子。
6. 一方获胜或认输后，双方看到相同结果；重复结束请求不会新增结果记录或重复计分。
7. 现有 AI 五种模式及认证、积分、迁移相关测试继续通过；补充在线对战的服务层并发测试和双浏览器端到端验证。

## 8. 建议实施顺序

1. 确定产品规则：房间过期时间、认输结果、是否计分，以及同一账号与 AI 对局能否并行。
2. 新建独立在线对局模型与 Flyway 迁移；完成创建、加入、落子、结果的服务层测试。
3. 增加 HTTP API 和大厅/房间/对局页面，以轮询完成双人闭环。
4. 验证并发落子、刷新恢复、后端重启恢复和现有模式回归。
5. 体验稳定后再增加 WebSocket 推送；只有在多实例或实际性能需求出现时再考虑 Redis。

## 9. 待用户确认的产品决策

以下是本文采用的建议默认值，实现前应确认：房主执黑；仅经典 15×15 规则；第一版不计入 AI 积分；断线不自动判负；开局后离开需主动认输；不做悔棋/计时；房间码短期有效。若希望采用随机执色、排位积分或掉线超时判负，范围和工期都需要重新评估。
